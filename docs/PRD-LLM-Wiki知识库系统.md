> 版本：v1.1
> 日期：2026-08-27
> 状态：草案
> 变更：v1.1 — 基于 PRD/TRD 交叉审查，对齐技术实现偏差（六阶段流水线、页面格式、GraphRAG 策略、原子性等）

---

## 1. 产品概述

### 1.1 背景

企业内部散落着大量文档（Markdown、TXT 等），传统 RAG 系统每次问答都从原始文档重新检索、重新组装、重新推理，知识无法积累。员工重复提问、跨文档综合困难、知识随人员流动流失。

### 1.2 产品定位

一个面向企业团队内部的 **LLM Wiki 知识库系统**。系统不仅存储和检索文档，还通过 LLM 流水线自动将原始文档蒸馏为结构化、互链的 Wiki 知识库，并构建可视化知识图谱。知识随文档增加而持续积累、自我演进。

核心范式转变：

```
传统 RAG：原始文档 → [检索] → LLM → 一次性回答（丢弃）
LLM Wiki：原始文档 → [ingest] → Wiki（持久化、持续更新）→ [检索] → LLM → 回答
```

### 1.3 目标用户

企业内部团队成员，需要基于团队文档进行知识查询、学习和综合分析。

### 1.4 核心价值

| 价值 | 说明 |
|---|---|
| 知识复利 | 文档越多，Wiki 越丰富，回答质量越高，而非每次从零开始 |
| 自动维护 | 系统自动撰写、互链、更新 Wiki，人工只需审核和补充 |
| 可溯源 | 每个回答、每个 Wiki 段落都可追溯到原始文档出处 |
| 可观测 | 完整的 LLM 调用链路、检索过程、Wiki 流水线各阶段可视化 |

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **团队（Workspace）** | 资源隔离的基本单位，知识库、文档、成员都归属于团队 |
| **源知识库（Source KB）** | 存储原始上传文档的知识库，类型为 `document` |
| **Wiki 知识库（Wiki KB）** | 由流水线自动生成和维护的 Wiki，类型为 `wiki`，绑定一个或多个 Source KB |
| **Wiki 页面** | Wiki 中的一篇 Markdown 页面，有明确的类型（索引/摘要/实体/概念/综述/分析） |
| **知识图谱** | 从文档中抽取的实体及其关系，支持可视化浏览和图谱检索 |
| **Chunk（分块）** | 文档经过切分后的最小检索单元，携带标题路径上下文 |
| **Ingest（摄入）** | 新文档加入 Source KB 后，触发六阶段流水线读取文档并增量更新 Wiki 的过程 |

### 2.1 Source KB 与 Wiki KB 的关系

- Source KB 和 Wiki KB 是**分离的**两类知识库
- 一个 Wiki KB 可绑定一个或多个 Source KB，形成"原始资料 → 综合知识"的关系
- Source KB 中的文档是不可变的原始资料（ground truth），系统只读不写
- Wiki KB 中的页面由流水线自动生成和维护，用户可浏览、编辑
- 一个团队可有多个 Source KB 和多个 Wiki KB，自由组合绑定

## 3. 用户角色与权限

### 3.1 角色定义

系统采用三级角色，角色在团队内分配：

| 角色 | 定位 |
|---|---|
| **管理员（Admin）** | 团队管理者，负责成员管理、知识库设置、系统配置 |
| **编辑者（Editor）** | 知识贡献者，可上传/删除文档、触发 Wiki 生成、编辑 Wiki、问答 |
| **查看者（Viewer）** | 知识消费者，可浏览知识库和 Wiki、使用问答，不可修改内容 |

### 3.2 权限矩阵

| 操作 | 管理员 | 编辑者 | 查看者 |
|---|:---:|:---:|:---:|
| 邀请/移除成员、分配角色 | ✅ | ❌ | ❌ |
| 创建/删除知识库 | ✅ | ❌ | ❌ |
| 修改知识库设置（分块、模型等） | ✅ | ❌ | ❌ |
| 上传文档 | ✅ | ✅ | ❌ |
| 删除文档 | ✅ | ✅ | ❌ |
| 触发 Wiki 生成/更新/重建 | ✅ | ✅ | ❌ |
| 编辑 Wiki 页面 | ✅ | ✅ | ❌ |
| Wiki 页面版本回滚 | ✅ | ✅ | ❌ |
| 浏览知识库/Wiki/图谱 | ✅ | ✅ | ✅ |
| 使用问答 | ✅ | ✅ | ✅ |
| 查看审计日志 | ✅ | ❌ | ❌ |
| 配置模型（LLM/Embedding） | ✅ | ❌ | ❌ |
| 查看可观测性面板 | ✅ | ✅ | ❌ |

一个用户可属于多个团队，在不同团队中可拥有不同角色。

## 4. 功能需求

### 4.1 用户认证与团队管理

#### 4.1.1 注册与登录

- 用户通过**账号密码**注册和登录
- 首次注册的用户自动创建一个团队并成为管理员
- 登录后进入团队切换/选择界面

#### 4.1.2 团队管理

- 支持创建多个团队
- 团队间数据完全隔离（知识库、文档、Wiki、对话互不可见）
- 管理员可通过邮箱/用户名邀请成员加入团队并分配角色
- 管理员可移除成员、修改成员角色
- 支持团队重命名

#### 4.1.3 审计日志

- 管理员可查看团队审计日志
- 记录：谁、什么时间、做了什么操作（文档上传/删除、Wiki 生成/编辑/回滚、成员变更、知识库设置变更等）
- 日志不可删除，支持按操作类型和时间筛选

---

### 4.2 源知识库管理

#### 4.2.1 创建 Source KB

- 用户可创建源知识库，填写：名称、描述
- 创建时配置：
  - **分块策略参数**（chunk 大小、重叠大小，使用默认值即可）
  - **Embedding 模型**（选择 Ollama 本地模型或 OpenAI API，选定后不可更改）
- 知识库支持启用/停用（停用后不参与检索）

#### 4.2.2 知识库列表

- 展示团队下所有知识库（Source KB 和 Wiki KB 分区展示）
- 每个知识库卡片显示：名称、描述、文档数、最近更新时间、状态
- 支持关键词搜索和标签筛选

#### 4.2.3 文档标签

- 文档支持多标签标记
- 可按标签筛选文档
- 标签可增删改

---

### 4.3 文档管理

#### 4.3.1 支持格式

支持以下格式：
- **Markdown**（`.md`）
- **纯文本**（`.txt`）

#### 4.3.2 文件上传

- 支持单文件上传和批量上传
- 上传流程：
  1. 前端选择文件
  2. 后端计算文件 **SHA-256 哈希**
  3. 在同一知识库内查重：若相同哈希已存在，返回提示"该文件已存在"，拒绝重复上传
  4. 存储文件，创建文档记录（状态：待处理）
  5. 入队异步解析任务
  6. 异步执行：读取文件 → 分块 → 向量化 → 写入向量索引
  7. 更新文档状态（处理中/已完成/失败）
- 上传时可选择标签
- 文档列表实时显示处理状态（待处理/处理中/已完成/失败+错误原因）
- 失败的文档支持重试

#### 4.3.3 文档列表与详情

- 文档列表展示：文件名、类型、标签、分块数、上传时间、上传者、状态
- 支持按文件名搜索、按标签筛选、按上传时间排序
- 文档详情：
  - 原文预览（Markdown 渲染）
  - 分块列表（展示每个 chunk 的内容、header_path、序号）
  - 文档元信息

#### 4.3.4 文档删除

- 删除文档时同时删除其所有分块和向量索引
- 删除操作记入审计日志
- 若该文档已被 Wiki KB 摄入，删除后 Wiki KB 中对应来源页标记为"来源已删除"，不自动删除 Wiki 页面（由管理员决定是否清理）

### 4.4 文档分块

#### 4.4.1 Header 路径感知切块（Markdown）

Markdown 文档按标题层级切分，每个 chunk 保留其在文档中的标题路径：

- 按 `#`（H1）、`##`（H2）、`###`（H3）标题边界切节
- 每个 chunk 记录 `header_path` 字段（标题数组）：
  - 遇到 H1 → 重置 path 为 `[H1标题]`
  - 遇到 H2 → path 为 `[最近的H1, H2标题]`
  - 遇到 H3 → path 为 `[最近的H1, 最近的H2, H3标题]`
- 每个 chunk 携带的 header_path 形如：`["产品介绍", "计费方式", "关键词快车"]`

#### 4.4.2 超长章节二次切分

- 若某个标题下的内容超过 chunk 大小上限（默认 512 字符），在该节内按段落/句子递归切分
- 二次切分产生的所有子 chunk **共享同一个 header_path**
- 相邻 chunk 间保留 80 字符重叠（overlap），标题边界处不重叠

#### 4.4.3 纯文本切分（TXT）

- TXT 文件无标题结构，采用递归字符切分
- 默认 512 字符 + 80 字符重叠
- `header_path` 为空

#### 4.4.4 Chunk 数据结构

每个 chunk 包含：

| 字段 | 说明 |
|---|---|
| content | chunk 文本内容 |
| header_path | 标题路径数组（TXT 为空） |
| seq | 在文档中的序号 |
| start_pos / end_pos | 在原文中的字符起止位置 |
| document_id | 所属文档 ID |
| kb_id | 所属知识库 ID |

#### 4.4.5 向量化时的上下文拼接

- 生成 embedding 时，输入文本为：`" > ".join(header_path) + "\n" + content`
- 使向量携带文档结构上下文，提升检索准确率
- BM25 全文检索同样将 header_path 拼入索引文本

#### 4.4.6 分块预览

- 知识库设置中提供分块预览功能
- 用户可粘贴一段 Markdown/TXT 文本，预览切分结果
- 展示每个 chunk 的 header_path、字符数、内容预览
- 用于调整 chunk 大小和重叠参数

### 4.5 Wiki 知识库

#### 4.5.1 创建 Wiki KB

- 创建 Wiki KB 时填写：名称、描述
- **绑定一个或多个 Source KB**（至少绑定一个）
- 可后续修改绑定关系（新增/移除 Source KB）
- 配置：
  - Wiki 生成使用的 LLM 模型（OpenAI / DeepSeek）
  - LLM 超时时间（默认 60 秒）和重试次数（默认 3 次）
  - 温度参数（默认 0.7）
  - 新文档上传后是否自动触发 Wiki 更新（默认关闭，手动触发）

#### 4.5.2 Wiki 页面类型

Wiki KB 包含以下六类页面，由流水线在 ingest 过程中按需创建和更新：

| 页面类型 | 目录 | 生成时机 | 内容 |
|---|---|---|---|
| **索引页** | `index.md` | 每次 ingest 后更新 | Wiki 内容目录，按分类列出所有页面链接 |
| **来源摘要页** | `source/` | 每篇新文档摄入时必生成 | 单文档核心内容提炼、关键实体/概念清单 |
| **实体页** | `entity/` | 流水线识别到人物/组织/产品/项目等实体时 | 实体描述、属性、关联实体、出处 |
| **概念页** | `concept/` | 流水线识别到术语/理论/方法/技术时 | 定义、上下文解释、关联概念、出处 |
| **全局综述页** | `overview.md` | 首批文档摄入后生成，后续增量更新 | 跨文档全局综述，综合所有来源摘要 |
| **分析页** | `analysis/` | 流水线发现跨文档对比/趋势/矛盾时主动创建 | 对比分析、趋势总结、矛盾标注等 |

> 操作审计由 `audit_logs` 表和页面修订历史（`wiki_page_revisions`）承担，不设独立 log 页面。

#### 4.5.3 页面内容结构

每个 Wiki 页面由**数据库元信息字段**和 **Markdown 正文**两部分组成：

**数据库字段：**

| 字段 | 说明 |
|---|---|
| slug | 页面唯一标识，如 `entity/tencent`、`concept/rag`、`source/{doc_id}` |
| title | 页面标题 |
| page_type | index / source / entity / concept / overview / analysis |
| summary | 一句话摘要（LLM 输出首行 `SUMMARY: ...`，解析后存入此字段） |
| category_path | 主题分类路径，如 `["组织"]`、`["技术","AI"]`，最多 2 级 |
| aliases | 别名数组，用于双链匹配和实体检索 |
| source_refs | 来源文档 ID 数组 |

**Markdown 正文格式：**

```markdown
SUMMARY: 腾讯是一家中国互联网科技公司，业务涵盖社交、游戏、云计算等。

## 基本信息

腾讯（Tencent）成立于1998年，总部位于深圳……

## 业务

- **社交**：微信、QQ
- **游戏**：全球最大游戏公司之一
- **云计算**：腾讯云

## 关键要点

- 微信月活超过13亿
- 2023年研发投入超过600亿元
```

- 正文首行为 `SUMMARY:` 摘要行，后处理时解析为 summary 字段，不渲染在正文中
- 页面间使用 `[[slug|显示名称]]` 双链语法互链（slug 唯一，避免重名歧义）
- 关联关系不写在正文固定章节中，而是通过 `[[双链]]` 和知识图谱（entities/relations 表）体现
- 所有页面同时进入向量索引，参与检索

#### 4.5.4 Wiki 生成（Ingest）

**触发方式：**
- **手动触发**（默认）：Wiki KB 详情页点击"生成/更新 Wiki"按钮
- **自动触发**（可选）：绑定的 Source KB 有新文档上传后自动触发
- 自动触发时采用 **debounce 合并**：30 秒内多次上传合并为一个批次处理

**执行流程（六阶段流水线）：**

Wiki 生成采用固定六阶段流水线，每阶段职责单一、可独立观测：

1. **抽取（Extract）**：对每篇新文档，LLM 抽取实体/概念骨架（name、slug、aliases、description），传入已有 slug 列表保证连续性
2. **引用标注（Citation）**：将文档 chunk 分批，LLM 标注每个候选 slug 引用了哪些 chunk（`{slug: [chunk_id]}`），可发现新 slug
3. **分类规划（Taxonomy）**：单次 LLM 调用为新 slug 分配 category_path（最多 2 级主题分类），复用已有分类
4. **来源摘要（Summary）**：对每篇文档，LLM 生成来源摘要页（SUMMARY 行 + Key Takeaways + 自动双链）
5. **归并写入（Reduce）**：对每个 entity/concept slug，收集其引用的 chunk 原文 + 已有页面内容，LLM 归并生成/更新页面（按 slug 加锁，串行写入）
6. **后处理（Post-process）**：双链注入、死链清理、内部引用标记剥离、更新 overview.md 和 index.md、新/更新页面重新向量化

- 每个 slug 的页面写入在单事务中完成（页面更新 + 修订快照 + 实体/关系）
- 以文档为粒度追踪任务状态，一个文档失败不回滚其他已成功页面，失败文档可单独重试
- 新/更新页面写入数据库并重新向量化
- 记录操作到审计日志

**并发控制：**
- 同一 Wiki KB 同时只允许一个 ingest 任务运行（加锁）
- 若已有任务在运行，新触发返回"Wiki 正在更新中，请稍后"

**全量重建：**
- 管理员可触发"全量重建"：清空所有 Wiki 页面，从绑定的 Source KB 重新生成
- 全量重建前需二次确认
- 重建过程中 Wiki KB 不可查询（显示"重建中"状态）

#### 4.5.5 Wiki 生成流水线

Wiki 生成采用**结构化六阶段流水线**，而非 ReAct 自由循环。流水线每阶段职责单一、可独立观测和重试：

| 阶段 | 名称 | LLM 调用 | 说明 |
|---|---|---|---|
| 1 | Extract | 每文档 1 次 | 抽取实体/概念骨架（name/slug/aliases/description），保证 slug 连续性 |
| 2 | Citation | 每文档分批 | 标注每个 slug 引用了哪些 chunk，可发现新 slug |
| 3 | Taxonomy | 每批次 1 次 | 为新 slug 分配 category_path（最多 2 级），复用已有分类 |
| 4 | Summary | 每文档 1 次 | 生成来源摘要页（SUMMARY + Key Takeaways + 双链） |
| 5 | Reduce | 每 slug 1 次 | 归并 chunk 原文 + 已有页面，生成/更新实体/概念页，写入实体关系 |
| 6 | Post-process | overview 1 次 | 双链注入、死链清理、index/overview 更新、重新向量化 |

- 流水线各阶段的 LLM 输入/输出均记录到 Langfuse，可在可观测性面板中按阶段查看
- 阶段 5 归并按 slug 加锁串行执行，防止同一页面并发写入冲突
- Wiki 生成不使用 ReAct 自由循环模式

#### 4.5.6 Wiki 页面浏览

- **Wiki 浏览器**：左侧目录树（按 category_path 主题分类树组织），右侧 Markdown 渲染
- `[[双链]]` 可点击跳转
- 每个页面顶部显示：类型标签、标签、来源文档数、最后更新时间
- 支持全文搜索 Wiki 页面
- 来源文档可点击跳转到 Source KB 中的原文

#### 4.5.7 Wiki 页面编辑

- 用户可在浏览器中直接编辑 Wiki 页面的 Markdown 内容
- 编辑保存时创建一个新的修订快照（见 4.5.8）
- 编辑保存后页面重新向量化
- 人工编辑的页面在下次流水线更新时标记为"人工编辑过"，提示用户 review

#### 4.5.8 Wiki 页面版本管理

每次页面写入（系统自动生成或人工编辑）都创建一个**不可变修订快照**：

**修订记录字段：**

| 字段 | 说明 |
|---|---|
| revision_id | 修订版本 ID |
| page_id | 所属页面 ID |
| content | 该版本的完整 Markdown 内容 |
| editor_type | 编辑者类型：`agent` / `manual` |
| editor_id | 编辑者 ID（系统生成为 NULL，人工为用户 ID） |
| change_summary | 变更说明（系统自动生成或人工填写） |
| created_at | 创建时间 |

**版本功能：**
- 页面详情可查看版本历史列表（时间、编辑者、变更说明）
- 可查看任意历史版本的完整内容
- 支持任意两个版本间的**行级 diff 对比**（增删高亮）
- **一键回滚**：选定旧版本 → 以该内容创建一个新修订（不删除任何历史，满足审计要求）
- 若最新版本为系统生成（editor_type=agent）、上一版本为人工编辑，UI 醒目提示"系统已更新此页面，您的人工编辑在上一版本，请对比确认"

#### 4.5.9 知识图谱

**实体与关系存储：**
- 实体和关系存储在 PostgreSQL 关系表中，不引入独立图数据库
- `entities` 表：实体名称、类型、描述、首次出现文档、关联 Wiki 页面
- `relations` 表：源实体、目标实体、关系类型、出处文档

**图谱可视化：**
- Wiki KB 提供"图谱"视图
- 使用交互式图库展示实体节点和关系边
- 支持：缩放、拖拽、点击节点跳转到对应 Wiki 页面
- 支持按关系类型和实体类型筛选显示
- 节点大小/颜色按实体类型区分

**图谱来源：**
- 流水线在阶段 5（Reduce）归并写入页面时，LLM 同时输出实体关系列表，同步写入 entities/relations 表
- 实体与 Wiki 实体页/概念页双向关联

### 4.6 智能问答

#### 4.6.1 问答入口

- Web 端提供对话式问答界面
- 用户提问前选择要查询的知识库（可多选 Source KB 和/或 Wiki KB）
- 对话界面左侧为会话列表，右侧为对话区

#### 4.6.2 多路混合检索

问答时采用三路并行检索 + RRF 融合：

| 检索路径 | 说明 |
|---|---|
| **Dense 向量检索** | 问题向量化后，在 pgvector 中做余弦相似度检索，召回语义相关 chunk |
| **Sparse BM25 检索** | 问题分词后在 PostgreSQL 全文索引中做关键词检索，召回精确匹配 chunk |
| **GraphRAG 图谱检索** | 从问题中字符串匹配实体名/别名 → 沿知识图谱关系扩展 1 跳 → 召回关联实体的 Wiki 页面 chunk 作为补充 |

**融合策略：RRF（Reciprocal Rank Fusion）**

```
score(chunk) = Σ 1/(k + rank_i(chunk))    # k = 60
```

- 三路检索并行执行，各自返回 Top-K 结果
- 用 RRF 融合排名，无需调参，对各路分数尺度不敏感
- Wiki 页面 chunk 在融合时给予轻微权重加成（预综合内容质量更高）
- 融合后取 Top-N（默认 8）进入 LLM 上下文

#### 4.6.3 RAG 问答流程

```
用户提问
  → 加载对话历史
  → 查询改写（多轮上下文改写为独立查询）
  → 三路并行检索（向量 + BM25 + 图谱）
  → RRF 融合
  → 阈值过滤 + Top-N 截断
  → 组装 Prompt（含检索结果 + 对话历史）
  → LLM 流式生成回答
  → 返回回答 + 引用来源
```

- 回答采用**流式输出**（SSE），逐字显示
- 检索过程中前端展示 pipeline 进度（"正在检索知识库..."）

#### 4.6.4 引用溯源

- LLM 回答中的引用以角标标注（如 `[1]`、`[2]`）
- 回答底部列出引用来源列表：
  - 来源文档名称
  - chunk 的 header_path（如"产品介绍 > 计费方式"）
  - 匹配的文本片段
- 点击引用可跳转到原文对应位置
- 区分来源类型：原始文档 / Wiki 页面

#### 4.6.5 多轮对话

- 支持多轮上下文对话
- 每轮对话自动将上下文改写为独立查询再检索（避免指代不清）
- 对话历史持久化存储，上下文携带最近 10 轮（20 条消息），超出部分不进入上下文
- 会话标题自动生成

#### 4.6.6 会话管理

- 会话列表按时间分组展示
- 支持会话重命名、删除
- 每个会话记录所选知识库范围
- 新会话可选择推荐问题（基于知识库内容自动生成）

### 4.7 可观测性

集成 **Langfuse** 作为统一可观测性平台，覆盖以下维度：

| 观测维度 | 内容 |
|---|---|
| **LLM 调用链路** | 每次 LLM 调用的 prompt、response、token 用量、耗时、成本 |
| **检索过程** | 三路检索各自召回的 chunk、原始分数、融合后排名、最终进入上下文的 chunk |
| **Wiki 流水线** | 六阶段（Extract/Citation/Taxonomy/Summary/Reduce/Post-process）各自的 LLM 输入输出、耗时、token 用量；每文档/每 slug 的处理状态 |
| **文档解析进度** | 文档上传→分块→向量化各阶段状态和耗时 |
| **系统指标** | 任务队列深度、错误率、各模型调用统计 |

- 管理员和编辑者可访问可观测性面板
- 每次问答和 Wiki 生成都有唯一 trace ID，可在 Langfuse 中查看完整调用链
- 支持按 trace 搜索、按 token/成本排序

### 4.8 模型配置

#### 4.8.1 LLM 模型

支持两个 LLM 提供商：
- **OpenAI**（GPT-4o / GPT-4o-mini 等）
- **DeepSeek**（DeepSeek-V3 / DeepSeek-chat 等）

- 管理员在系统设置中配置 API Key 和 Base URL
- 每个知识库/Wiki KB 可独立选择使用的 LLM 模型
- 支持配置模型参数（温度、最大 token、超时时间）
- 提供"模型测试"按钮，验证配置是否可用

#### 4.8.2 Embedding 模型

支持两个 Embedding 提供商：
- **Ollama 本地**（默认，如 bge-m3、nomic-embed-text，需用户自行部署 Ollama 并拉取模型）
- **OpenAI API**（text-embedding-3-small，作为备选）

- 管理员配置 Ollama 服务地址或 OpenAI API Key
- 创建知识库时选择 Embedding 模型，选定后不可更改（维度不同，更换需重建索引）
- 向量维度由所选模型决定

## 5. 非功能需求

### 5.1 性能

| 指标 | 要求 |
|---|---|
| 问答首字延迟 | < 2 秒（流式输出） |
| 单文档解析（100KB Markdown） | < 10 秒 |
| Wiki ingest（单文档） | < 60 秒（取决于 LLM 响应速度） |
| 检索延迟（三路并行） | < 1 秒 |
| 并发问答 | 支持团队内 20 人同时使用 |

### 5.2 安全

- 用户密码加密存储（bcrypt）
- API Key 等敏感配置加密存储（AES-256-GCM）
- 团队间数据严格隔离
- 文档上传限制文件大小和类型（仅 .md/.txt）
- 所有写操作记入审计日志

### 5.3 部署

- **Docker Compose 一键部署**
- 核心容器：Web 前端、Python 后端、PostgreSQL（含 pgvector）、Redis、Langfuse
- 支持配置文件管理所有环境变量
- 支持数据持久化卷挂载

### 5.4 可用性

- 文档解析失败不影响其他文档，支持重试
- Wiki ingest 失败支持重试：以文档为粒度追踪状态，单个文档失败不影响其他文档；已成功生成的页面保留，失败文档可单独重试
- LLM API 调用失败有明确错误提示和重试机制

### 5.5 国际化

- 界面语言为中文
